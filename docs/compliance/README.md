# Compliance Evidence Archive

This directory holds daily SOC2 / ATO posture snapshots generated by the
`evidenceCollector` service. Each `evidence_YYYY-MM-DD.md` file is the
state of ABC's compliance posture at a moment in time — control coverage
counts, audit-log retention totals, PII detection volumes, model registry
status, retention-job last-run summary, and (when those features ship)
webhook delivery counts and budget enforcement stats.

## What lives in each snapshot

Every snapshot has these sections, generated independently so a missing
table in one section doesn't fail the whole pass:

1. **Header** — date, generated_at timestamp, snapshot schema version.
2. **Controls matrix** — count of in-place / partial / outstanding controls
   parsed from `docs/security/controls_matrix.md`.
3. **Audit log retention** — total rows, oldest entry timestamp, top-10
   action counts.
4. **PII detections** — count by classification over the trailing 30 days.
5. **Model registry** — active vs inactive models, plus active model count
   per max classification.
6. **Retention job** — last run timestamp (from `audit_log` rows where
   `action = 'admin.retention.run'`) and the structured details payload.
7. **Webhook deliveries** — last-24h count by status (delivered / failed /
   exhausted). Reports `not_applicable_yet` until Bot 21's
   `webhook_deliveries` table exists.
8. **Token budgets** — count per scope_type. Reports `not_applicable_yet`
   until Bot 15's `token_budgets` table exists.
9. **Footer** — generator version string.

Sections that can't be collected (missing table, transient DB failure,
unreadable controls matrix) degrade to a `not_applicable_yet` block with a
short reason. The pass never fails wholesale.

## How snapshots are generated

There are two entry points.

### Daily scheduler (production)

When `EVIDENCE_JOB_ENABLED=true` and the backend boots, a daily timer
arms at `EVIDENCE_JOB_HOUR` (default `03` — one hour after the retention
job). Each pass writes to `docs/compliance/evidence_YYYY-MM-DD.md`,
overwriting any same-day file.

Required environment:

| Variable | Default | Notes |
|----------|---------|-------|
| `EVIDENCE_JOB_ENABLED` | `false` | Turn on in production after reviewing the schedule. |
| `EVIDENCE_JOB_HOUR` | `3` | UTC hour-of-day for the daily pass. |
| `DATABASE_URL` | unset | Required for the DB-backed sections. The collector degrades each section to `not_applicable_yet` when unset. |

### Admin endpoint (on-demand)

Authenticated admin users can trigger a fresh snapshot any time:

```bash
# Generate a fresh snapshot
curl -X POST -b "$ABC_SESSION" https://abc.gov.ab.ca/api/compliance/evidence/run

# Read the most recent snapshot's Markdown
curl -b "$ABC_SESSION" https://abc.gov.ab.ca/api/compliance/evidence/latest
```

The `run` endpoint returns the full JSON snapshot **and** the Markdown body
in the response — the admin UI uses the JSON to render counts; tools
fetching the artifact for an audit packet usually want the Markdown.

## Why Markdown

The snapshot is a compliance artifact that reviewers read end-to-end. Plain
Markdown is:

- **Diff-able.** Two snapshots from consecutive days highlight what
  changed — perfect for incident timeline reconstruction.
- **Archivable.** A reviewer can attach the file to a ticket, a SOC2
  control package, or a FOIP response without rendering it through any
  tool.
- **Future-proof.** Markdown will outlive any UI we build in front of it.

The same data is also available as a JSON snapshot from the `run`
endpoint for programmatic consumers (admin UI, dashboards).

## What this is *not*

This is **not** the audit log. The audit log is the per-request stream of
who-did-what — it's authoritative for "did this action happen?" The
evidence collector is the periodic *posture* snapshot — "what did the
system look like on Day N?"

This is **not** PII or session data. The snapshot contains aggregate
counts only, never individual records.

This is **not** a substitute for the controls matrix. The matrix
(`docs/security/controls_matrix.md`) is the spec of what we promise to
implement; the snapshot reports on the live state of those promises.

## ATO renewal checklist

For an ATO renewal, attach:

1. The most recent two evidence snapshots (week-over-week diff).
2. The current controls matrix.
3. The most recent Red/Blue agent report (`docs/security/red_blue_report.md`).
4. The most recent PIA (`docs/privacy/pia.md`).

The evidence snapshots cover items 1, 2 (by reference), and provide quick
sanity checks against the matrix.

## Adding a new section

To extend the snapshot:

1. Add a typed section interface to `backend/src/services/evidenceCollector.ts`.
2. Add a `collect<Section>()` async function that catches its own errors
   and returns either `{ status: "ok", ... }` or `notApplicable(...)`.
3. Wire it into the `Promise.all` in `collectEvidence()`.
4. Add a Markdown renderer block in `formatEvidenceMarkdown()`.
5. Cover the section in `evidenceCollector.test.ts` — both the happy path
   and the missing-table degradation.

Sections must be **independent** — never depend on another section's
result. This keeps the pass idempotent and partial-failure-tolerant.

## Operational notes

- The daily pass overwrites the same-day file. If you need to keep multiple
  snapshots on a single day (e.g. before-and-after a deploy), copy the file
  manually before triggering the next run.
- The collector writes to the repo's `docs/compliance/` directory. In a
  containerised deployment, mount this directory as a persistent volume or
  redirect via `setEvidenceOutputDir()` at boot.
- A future bot will wire a `.github/workflows/evidence.yml` cron that runs
  the pass against staging and commits the result to the repo — see the
  follow-ups in Bot 22's coordination doc entry.
